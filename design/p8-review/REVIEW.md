### R2 — MAJOR — FAIL: lost-response retries abandon request identity

Evidence: [ProductRepositoryImpl.kt:73](../../android/data/src/main/kotlin/top/alanvampuke/dininglog/data/ProductRepositoryImpl.kt#L73) calls requestFor on every submit, and [ProductApi.kt:172](../../android/data/src/main/kotlin/top/alanvampuke/dininglog/data/remote/ProductApi.kt#L172) generates a fresh UUID every time. SaveInput carries no OriginalRequest ([Writes.kt:10](../../android/core/src/main/kotlin/top/alanvampuke/dininglog/core/Writes.kt#L10)). Failure retains only that input ([ProductRepositoryImpl.kt:105](../../android/data/src/main/kotlin/top/alanvampuke/dininglog/data/ProductRepositoryImpl.kt#L105)).

Concrete failure: a CREATE succeeds on the server, but its response is lost. The editor correctly displays “保存失败，请检查网络后重试”. Clicking Save again sends the same entity ID with a new idempotency key. The unchanged backend rejects the existing ID with ID_CONFLICT ([mutations.ts:52](../../backend/src/domain/mutations.ts#L52)); the repository maps that error back to the same network-retry message ([ProductRepositoryImpl.kt:99](../../android/data/src/main/kotlin/top/alanvampuke/dininglog/data/ProductRepositoryImpl.kt#L99)). Further unchanged retries cannot acknowledge the successful creation. A new record has no existing detail page beneath its editor, so the existing-detail refresh workaround does not resolve this flow directly. Updates also lose replay identity and can turn a successful write into a needless version conflict.

The former replay assertion was replaced by leaving the editor and refreshing an existing restaurant in [ProductEndToEndTest.kt:250](../../android/app/src/androidTest/kotlin/top/alanvampuke/dininglog/product/ProductEndToEndTest.kt#L250). That verifies the specified refresh alternative, but does not verify the Save button's retry behavior or the CREATE case. [DirectSaveTest.kt:72](../../android/data/src/test/kotlin/top/alanvampuke/dininglog/data/DirectSaveTest.kt#L72) checks one lost-response attempt, not a subsequent retry.

Minimal fix: at [ProductRepositoryImpl.kt:68](../../android/data/src/main/kotlin/top/alanvampuke/dininglog/data/ProductRepositoryImpl.kt#L68) and [ProductApi.kt:143](../../android/data/src/main/kotlin/top/alanvampuke/dininglog/data/remote/ProductApi.kt#L143), retain the prepared method/path/payload/key in memory and reuse it for an unchanged retry. Clear it after acknowledgement or a resolved conflict; do not reuse a key for changed payloads. If input changes after an uncertain result, reconcile that pending operation before treating the changed values as a fresh write. This requires no persisted draft or process-death restoration. Add a committed-CREATE/lost-response/unchanged-retry test that requires the original key/body, one creation and a Saved result.

### R3 — MAJOR — FAIL: activity recreation silently replaces unsaved input

Evidence: MainActivity obtains ProductViewModel through the retained ViewModel store ([MainActivity.kt:117](../../android/app/src/main/kotlin/top/alanvampuke/dininglog/MainActivity.kt#L117)). Recreating its Compose navigation runs LaunchedEffect(route) again and calls openEditor ([ProductRoot.kt:165](../../android/feature/src/main/kotlin/top/alanvampuke/dininglog/feature/ProductRoot.kt#L165)). That method unconditionally sets a fresh loading state ([ProductViewModel.kt:172](../../android/feature/src/main/kotlin/top/alanvampuke/dininglog/feature/ProductViewModel.kt#L172)), reconstructs default or cached fields and replaces the editor ([ProductViewModel.kt:175](../../android/feature/src/main/kotlin/top/alanvampuke/dininglog/feature/ProductViewModel.kt#L175), [ProductViewModel.kt:185](../../android/feature/src/main/kotlin/top/alanvampuke/dininglog/feature/ProductViewModel.kt#L185)).

Concrete failure: enter a new restaurant name or edit a note, then rotate the device. Even while the same process and ViewModel remain alive, the repeated openEditor call replaces the in-memory input. New restaurant fields reset; existing edits revert to cached values. It also resets the saving flag if recreation occurs during submission. The task permits losing input after process death, not silently discarding live in-memory input on ordinary recreation. The current test covers clearing on explicit leave ([ProductViewModelTest.kt:186](../../android/feature/src/test/kotlin/top/alanvampuke/dininglog/feature/ProductViewModelTest.kt#L186)), not reopening the same active editor after recreation.

Minimal fix: at [ProductViewModel.kt:170](../../android/feature/src/main/kotlin/top/alanvampuke/dininglog/feature/ProductViewModel.kt#L170), return without initialization when the current editor already belongs to the requested ref and operation, preserving input, errors/conflict and saving state. Reinitialize after leaveEditor or when opening another operation. Retain the route identity checks at [ProductRoot.kt:165](../../android/feature/src/main/kotlin/top/alanvampuke/dininglog/feature/ProductRoot.kt#L165). Verify activity recreation for CREATE and UPDATE, and during an in-flight save, while still asserting that a newly created ViewModel does not restore unsaved fields.

### R6 — MINOR — PARTIAL: abrupt process interruption leaves partial package files

Evidence: download writes directly to the final app-<versionCode>.apk path ([InAppUpdates.kt:28](../../android/app/src/main/kotlin/top/alanvampuke/dininglog/InAppUpdates.kt#L28), [InAppUpdates.kt:94](../../android/app/src/main/kotlin/top/alanvampuke/dininglog/InAppUpdates.kt#L94)). Ordinary cancellation/errors delete it ([InAppUpdates.kt:118](../../android/app/src/main/kotlin/top/alanvampuke/dininglog/InAppUpdates.kt#L118)), and the service delays CANCELED until cleanup ([UpdateDownloadService.kt:49](../../android/app/src/main/kotlin/top/alanvampuke/dininglog/UpdateDownloadService.kt#L49), [InAppUpdates.kt:50](../../android/app/src/main/kotlin/top/alanvampuke/dininglog/InAppUpdates.kt#L50)). However, START_NOT_STICKY ([UpdateDownloadService.kt:55](../../android/app/src/main/kotlin/top/alanvampuke/dininglog/UpdateDownloadService.kt#L55)) and purely in-memory update state ([InAppUpdates.kt:23](../../android/app/src/main/kotlin/top/alanvampuke/dininglog/InAppUpdates.kt#L23)) provide no startup sweep or recovery for files left when the process dies. A later retry of the same version overwrites its file, but abandoned versions can remain. The supplied evidence explicitly excludes this lifecycle scenario ([evidence.json:330](../../design/bite/p8-evidence/evidence.json#L330)).

Suggested fix: write unverified content to a .part file and prune abandoned .part files when initializing the update directory; rename only after verification. Keep the existing SHA check before installation. This is a cleanup/lifecycle issue, not evidence that an unchecked APK can be installed.

### R7 — MINOR — PARTIAL: transport failures can bypass the readable Chinese retry message

Evidence: [InAppUpdates.kt:123](../../android/app/src/main/kotlin/top/alanvampuke/dininglog/InAppUpdates.kt#L123) forwards arbitrary IOException.message verbatim, and [UpdateDialog.kt:35](../../android/feature/src/main/kotlin/top/alanvampuke/dininglog/feature/settings/UpdateDialog.kt#L35) displays it. A socket timeout or disconnect can therefore show low-level English transport text instead of an actionable localized explanation. The download-page button remains available, so the fallback control itself is present.

Suggested fix: at [InAppUpdates.kt:123](../../android/app/src/main/kotlin/top/alanvampuke/dininglog/InAppUpdates.kt#L123), distinguish the downloader's deliberate user-facing HTTP/incomplete-download errors from transport exceptions; map the latter to “下载失败，请检查网络后重试或打开下载页”. Preserve technical causes for diagnostic logging.
