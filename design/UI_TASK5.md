## 二、`design/PLAN.md` 同步修订（定点 patch，不要整篇重写）

### 1. 评分精度 0.1

- 全文把「1～5 整数评分」「可空的 1～5 整数」改为「**可空的 1.0–5.0 评分，精确到 0.1**」
- 存储方案改成：**D1 用 INTEGER 存十分位**，即 `rating_tenths INTEGER`，1.0 存 10、4.3 存 43，`CHECK (rating_tenths BETWEEN 10 AND 50)`，NULL 表示未评分
  - 在文档里说明为什么不用 REAL：浮点在 JSON 往返和比较里会引入 4.300000000000001 之类的噪声，十分位整数是精确的；API 层输出仍然是 `4.3` 的数字，由服务端做 `tenths/10` 转换
- 所有出现 `CHECK (rating BETWEEN 1 AND 5)` 的 DDL 都要改；`rating` 字段名统一改 `rating_tenths`
- diff / revision 里记录的旧值新值也按十分位存，展示时除以 10
- 校验规则补：拒绝 0、拒绝 >50、拒绝非整数 tenths

### 2. 菜品不再是独立 tab，归到餐厅

- 页面地图与底部导航：底部导航固定为 **「餐厅」「到店」「我的」** 三个，删除任何「菜品」独立一级页
- 菜品库是餐厅详情下的二级页，路由 `/restaurants/{id}/dishes`
- 补充说明：菜品的增删改入口都在餐厅内（餐厅详情 → 这家店的菜 → 新增/编辑/删除），不做全局菜品列表页

- 检查并删除文档里任何「全局菜品列表」「菜品 tab」的描述

### 3. 搜索覆盖餐厅 + 菜品 + 评价 + 备注

当前 search_text 只索引餐厅级字段。改为：

- 新增一节说明搜索范围：餐厅名称、菜系、地址、餐厅评价、餐厅备注、**菜品名称、菜品短评**
- 方案：新增**反规范化搜索索引表** `restaurant_search`（`restaurant_id` 主键，`content` TEXT 为聚合文本，`updated_at`），在餐厅或任一菜品有效变更时**在同一 batch 内重建**该餐厅的聚合文本
  - 不在查询时 JOIN dishes 做全表扫描，也不依赖 FTS5 中文分词
  - 聚合文本做 NFKC + lowercase + 空白规整，用 `instr(content, ?)` 匹配
- 搜索结果要能返回**命中的字段类型**（restaurant / dish / review / note），用于 UI 显示「菜品『辣子鸡』匹配」
- 更新容量估算：聚合文本会让存储增加，说明增加量与估算（每家餐厅约 8 道菜 × (菜名 + 短评) ≈ 300–600 字节，500 家约 0.15–0.3 MB，可忽略）
